## 2. Контекст и цели

### 2.1. Бизнес-цели (выведены из ТЗ)

1. Централизованно управлять парком экранов в партнёрских сетях.
2. Размещать коммерческий, собственный и нейтральный контент с учётом квот эфирного времени.
3. Давать организациям изолированный ЛК с ролями, фильтрами и отчётностью.
4. Обеспечивать непрерывную управляемую работу устройств (питание/включение/мониторинг).
5. Масштабировать модель признаков (тегов) без жёсткой иерархии фильтров.
6. (Перспектива) Подключить ИИ для классификации контента (сфера деятельности и др.).

### 2.2. Границы (as-is по документу)

**In scope (заявлено):**

- Регистрация мониторов/станций, ориентация, признаки
- Загрузка статичных макетов и видео (до Full HD / 4K)
- Шаблоны статичных изображений с редактируемыми зонами
- Плейлисты: циклические и по таймингу, вставки, автозаполнение
- Разделение эфирного времени между организациями/типами контента
- ЛК, роли, мультиорганизационность, несколько баз вещания
- Отчёты: выходы, загруженность, финансовые калькуляторы
- Кроссплатформенное ПО плеера (в т.ч. Linux), минимум кабелей (кроме 220В)
- Управление питанием/включением монитора

**Out of scope / не описано явно:**

- Конкретный hardware (SoC, STB, Smart TV, Android/Linux-агент)
- CMS для динамических меню вне шаблонов
- Биллинг/оплата (есть только расчёт долей в отчёте)
- Мобильное приложение
- Юридические/лицензионные аспекты контента

## 3. Стейкхолдеры и роли

### 3.1. Модель владения и тенантов (зафиксировано)

- **Заказчик системы** = оператор рекламной сети.
- **Все точки принадлежат только оператору**; он владелец парка экранов.
- **Клиент сети** = отдельная организация со своим ЛК (тенант).
- Точка **не** принадлежит клиенту; на одной точке могут быть эфирные блоки нескольких клиентов.
- **Клиент видит весь парк точек** оператора (каталог для выбора).
- Клиент **самостоятельно выбирает и бронирует свободные квоты/эфирные блоки** на точке.
- В содержимом эфира клиент видит **только свой** забронированный блок (не чужой эфир).

### 3.2. Роли в ЛК клиента (зафиксировано)

| Роль (код) | Права в ЛК клиента |
|------------|--------------------|
| `manager` | Загрузка медиаматериалов; формирование плейлистов; формирование наборов точек; бронирование, **отмена и перенос** квот |
| `accountant` | Доступ к финансовым отчётам |
| `administrator` | Весь функционал ЛК клиента |

Возможность **добавлять роли** и **настраивать права** без перестройки ядра сохраняется.

### 3.3. Оператор сети (зафиксировано)

- Сотрудники оператора работают **только в Avo**.
- Отдельный ЛК оператора **не нужен**.
- **«Режим клиента»**:
  - **one-click из Avo** с **сохранением сессии Avo**;
  - в ЛК оператор действует с правами роли **`administrator` клиента**;
  - в аудите фиксируется **«сделано оператором X»** (не маскируется под пользователя клиента).
- В Avo оператор видит **все устройства**, **всех клиентов**, **все квоты всех клиентов**; может **отменять и переносить** брони клиентов.

### 3.4. Бронирование квот (зафиксировано)

- Бронирование слота — **мгновенная фиксация** (без hold/таймаута/модерации до закрепления).
- Конфликт на один слот при **первичной** брони: **first-write-wins**.
- Зафиксированную бронь можно **отменить** или **перенести** (`manager` клиента; оператор в Avo).
- **Перенос**:
  - возможен на **любую точку парка**;
  - **только на предварительно свободный** целевой слот (занятый — перенос невозможен, исходная бронь сохраняется);
  - приоритет «уже держал старый слот» на целевой **не переносится** (F12);
  - на захват свободного целевого слота действует **first-write-wins** (F14) — как при новой брони.

### 3.5. Аутентификация в ЛК (зафиксировано)

- Пользователь входит в ЛК организации по **логину и паролю**.
- Учётная запись привязана к **организации** и **роли**.
- Права в ЛК определяются ролью (§3.2).
- Оператор в «режиме клиента»: one-click из Avo, права `administrator` клиента, аудит «оператор X» (§3.3).

> Ранее (п.10.1.3) допускалось «на старте все права у всех ролей» — **снято** решением F3: роли в ЛК разграничены сразу.

> **Открыто**: нужна ли оплата после фиксации брони.

## 7. Пользовательские сценарии (сквозные)

### US-A. Запуск точки

Админ регистрирует локацию → экран(ы) → ориентацию → признаки → делит эфирное время между орг-циями → назначает нейтральный пул.

### US-B. Коммерческое размещение

`manager` клиента в ЛК → видит весь парк точек → выбирает свободный слот → **мгновенная фиксация** (при гонке — first-write-wins) → загружает ролики / собирает плейлист → ставит в свой эфирный блок. Оператор работает в Avo; при необходимости заходит в ЛК клиента («режим клиента»).

### US-C. Циклический день

Система на точке собирает 20′ блок: коммерция в подблоках + нейтральные прослойки без повторов → крутит цикл; в HH:MM вставляет timed-ролики.

### US-D. Меню в кафе

Оператор выбирает шаблон → правит зоны (блюдо, цена, фото) → публикует на экраны с признаком `меню`.

### US-E. Отчётность

Менеджер выгружает справку выходов / упрощённую справку / фин.разбивку / загруженность.

## 9. Варианты оптимизации функционала

### 9.1. Продуктовая декомпозиция (рекомендуется)

| Этап | Состав | Ценность |
|------|--------|----------|
| **MVP-1** | Устройства + теги + медиатека + простой плейлист + окна расписания + play log | Уже близко к текущему проекту |
| **MVP-2 Airtime** | Квоты, типы контента, нейтральный пул, изоляция эфира орг-ций | Коммерческая модель сетей |
| **MVP-3 Scheduler** | Циклические блоки, подблоки, timed inserts, правила соседства | «Настоящий» эфир |
| **MVP-4 Templates** | Шаблоны меню/ценников | Кафе/аптеки |
| **MVP-5 Reporting+Finance** | Справки, загруженность, калькулятор долей | Закрытие продаж/аккаунтинга |
| **MVP-6 Fleet Ops** | Станционный агент: кэш N ч, HLS, VLC+ADB, health | Критичный edge |
| **MVP-7 Power** | Power management **через ADB** (агент) | После стабильного HLS runtime |

### 9.2. Упрощения без потери ценности

1. **Признаки = теги + фасеты**, не отдельная «БД признаков». Параллельная фильтрация = комбинация AND между выбранными фасетами / OR внутри фасета (зафиксировать семантику один раз).
2. **Иерархия обязательна**: `Location → Station → Screen` (станция не опциональна).
3. **Плейлист v1** = упорядоченный список ассетов; «циклический блок 20′» = *генератор расписания* (job/сервис), а не ручной конструктор каждый день.
4. **Нейтральный контент** = плейлист/пул с политикой `random_no_repeat_day`, подключаемый как filler-policy к квоте.
5. **Timed vs cyclic** свести к единой модели: `ScheduleItem { priority, window, mode: loop|exact|fill }`.
6. **Шаблоны** отложить: на первом этапе — готовые статичные PNG/JPEG из дизайна; зоны — когда появится поток «меню каждый день».
7. **Финансы** вынести из core-эфира: отчётный модуль на play log + формула; не блокировать эфир.
8. **Power management** — через **ADB** в станционном агенте (после стабильного HLS).
9. **Sync** — целевой drift **0.5–2 с** (HLS); frame-accurate **не требуется**.
10. **ИИ** — асинхронная классификация тегов; не в UX критического пути загрузки.

### 9.3. Архитектура edge (зафиксировано)

```text
Rails (кабинет + Avo + MediaTranscodeJob + Package API)
        │  пакет эфира (HTTPS / pull)
        ▼
Станция (Linux) ── станционный агент [ДОЧЕРНИЙ ПРОЕКТ]
        │  • кэш медиа (скользящее окно N ч)
        │  • HLS (-c copy) → HTTP
        │  • ADB → VLC на Android TV
        │  • power via ADB; health/stats
        ▼
Android TV + VLC  (sync соседних ТВ ~0.5–2 с)
```

| Решение | Статус |
|---------|--------|
| Sync 0.5–2 с | **Принято** |
| Плеер VLC + ADB | **Принято** (основной) |
| Кэш на станции | **Принято** |
| Трансляция HLS со станции | **Принято** |
| Станционный агент | **Принято**; отдельный дочерний проект; требования — §16 |
| Multicast UDP | **Отклонён** (MediaCodec) |

## 15. Наследие legacy-стека

> Источники: `tmp/stack.md`, `tmp/README_STREAM_GUIDE_RU.md` (июль 2026).  
> Работающая система на shell + ffmpeg + VLC/ADB; перестраиваем на **Rails** + **Android TV**. Веб-ЛК в legacy «не наш».

### 15.1. Целевая и фактическая архитектура legacy

**Целевой пайплайн (из гайда):**

```text
Веб-морда → POST manifest + video
  → GPU/prep-сервер: ffmpeg encode ОДИН РАЗ → .ts (GOP=25) + package.json
  → rsync → стрим-сервер: concat -c copy → HLS -c copy → httpd :8080
  → ADB → VLC на Android TV (HTTP HLS)
```

**Факт сейчас (временное):** один стрим-сервер часто **перекодирует на лету** (GOP исходников=50) → CPU ~60–80%; целевое — prep с GOP=25 и HLS `-c copy` → CPU ~1–2%.

**Синхронизация ТВ при HLS:** ~**0.5–2 с** drift (размер сегмента + буфер VLC), не frame-accurate.

### 15.2. Критический constraint: MediaCodec на Android TV

На проверенных ТВ (MediaTek/Realtek + VLC 3.0.21):

| Транспорт | Результат |
|-----------|-----------|
| HTTP static `.ts` / chunked | ✅ Работает |
| **HLS (HTTP)** | ✅ Работает — **рекомендуемый** |
| UDP / RTP multicast | ❌ MediaCodec падает |
| RTSP | ❌ падает |

Симптомы: `AMediaCodec.dequeueOutputBuffer failed`, артефакты, чёрный экран.  
**Вывод для Rails-проекта:** не строить edge на multicast/UDP/RTSP без отдельной валидации на целевом железе. Базовый путь — **HTTP (HLS или file playback)**.

### 15.3. Профиль кодирования (обязательный для HLS `-c copy`)

| Параметр | Значение | Зачем |
|----------|----------|-------|
| Видео | H.264 High, 1920×1080, 25 fps | Единый формат флота |
| **GOP / keyint** | **25** (1 с), `sc_threshold=0` | Нарезка HLS-сегментов 1 с без re-encode |
| Битрейт | ~5 Mbps CBR | Стабильный стрим |
| Аудио | AAC 128k, 48 kHz, stereo | |
| Контейнер | MPEG-TS, `+resend_headers` | SPS/PPS на IDR |
| PTS | `-muxdelay 0 -muxpreload 0`, `+genpts` | Иначе VLC: «picture way too early» |
| Склейка роликов | `ffmpeg concat -c copy` (не `cat *.ts`) | Нормализация PTS |

**Правило:** encode на prep-сервере/в Rails Job **один раз**; на станции — только `-c copy` (+ concat/HLS).

Опционально: VAAPI (`h264_vaapi`) на GPU-хосте; в текущем железе i915/VAAPI часто не настроен → fallback CPU libx264.

### 15.4. Что переиспользуем в Rails-проекте

| Legacy | Как использовать у нас | Куда ложится |
|--------|------------------------|--------------|
| **Двухэтапный пайплайн** prep → stream | Job транскода + артефакты; edge только копирует/раздаёт | Active Job + object storage |
| **Профиль GOP=25 / PTS=0** | Единый media profile | `MediaTranscodeJob` / ADR encoding |
| **HLS как рабочий транспорт** | Кандидат для станционной раздачи на группу ТВ | Station agent / TV app |
| **package/manifest JSON** | Контракт пакета эфира | Station Package API |
| **Плейлист + schedule + loop + tv_map** | Домен расписания и привязки экранов | Playlist / Schedule / ScreenGroup |
| **concat по order** | Сборка циклического блока дня | Генератор эфира |
| **Stream Stats API (Go :8081)** | Идеи эндпоинтов: health, system, stream, tvs, screenshot, record | Агент + кабинет/Avo (переписать, не обязательно Go) |
| **rsync distribute** | Доставка артефактов на станцию | HTTPS pull / агент-pull |
| **monitoring / doctor / WoL** | Ops и power | Healthchecks; WoL → MVP-7 |
| **ADB bootstrap** | Первичная настройка ТВ | Runbook; не основной runtime playback |

### 15.5. Что не переносим as-is

| Legacy | Почему | Чем заменяем |
|--------|--------|--------------|
| Чужой веб + `POST /package` | ЛК — ядро продукта | Rails кабинет + Avo |
| Shell целиком | Нет multi-tenant/RBAC/аудита/квот | Ruby + **станционный агент** |
| Холодный старт VLC через голый `am start -d` | Игнорирует URL | В агенте: **monkey + intent** (как в legacy) |
| **UDP/RTP multicast** | Не работает на целевых ТВ | **HLS/HTTP** |
| busybox httpd quirks | `Connection: close` | Нормальный HTTP в агенте |
| Хранение только `roliki/ts/` на «сервере эфира» | Нет тенантов | Active Storage + кэш на станции |

## 16. Требования к станционному агенту (дочерний проект)

> Агент разрабатывается **отдельным репозиторием/проектом**.  
> Этот раздел — контракт и scope для агента; Rails остаётся источником правды по эфиру, квотам, медиатеке.

### 16.1. Назначение

Промежуточное ПО на **Linux-станции** в локации:

1. Получает и **кэширует** пакет эфира (скользящее окно N часов).
2. Собирает/отдаёт **HLS** на локальные Android TV.
3. Управляет **VLC** на ТВ через **ADB** (старт URL, контроль сессии).
4. Выполняет **power management** экранов через **ADB**.
5. Отдаёт **health/stats** в Rails/Avo.

### 16.2. Границы ответственности

| В scope агента | Вне scope (Rails / другое) |
|----------------|----------------------------|
| Кэш медиа на диске станции | ЛК клиента, роли, квоты, бронирование |
| Применение package / каналы | Транскод GOP=25 (prep в Rails/worker) |
| HLS `-c copy` + HTTP | Биллинг, отчёты, финансы |
| ADB → VLC, power | Создание медиапланов |
| Локальный мониторинг ТВ | Мультитенантная изоляция данных |
| Регистрация станции / heartbeat | UI Avo (агент только API) |

### 16.3. Функциональные требования агента (AG)

| ID | Требование | Приоритет |
|----|------------|-----------|
| AG-01 | Регистрация/привязка к `station_id` оператора; аутентификация к Rails (token/mTLS — TBD) | Обязательно |
| AG-02 | Pull (или push) **пакета эфира** с Rails; проверка целостности/версии | Обязательно |
| AG-03 | Локальный **кэш** артефактов на N часов (N с конфигурации станции, default 24, скользящее окно) | Обязательно |
| AG-04 | Вытеснение устаревших файлов кэша за пределами окна | Обязательно |
| AG-05 | Материализация плейлиста: concat по `order` при необходимости (`-c copy`, PTS normalize) | Обязательно |
| AG-06 | Запуск/перезапуск **HLS** (`-c copy`, сегменты ~1 с, loop) без re-encode | Обязательно |
| AG-07 | HTTP-раздача HLS в LAN станции | Обязательно |
| AG-08 | Инвентарь ТВ станции (IP, ADB reachable); `adb connect` | Обязательно |
| AG-09 | Старт VLC на ТВ: monkey + intent + MIME `application/x-mpegURL` (учёт cold-start VLC) | Обязательно |
| AG-10 | Назначение HLS URL каждому ТВ по `tv_map` / назначению из пакета | Обязательно |
| AG-11 | Перезапуск стрима/VLC при сбое; идемпотентный apply package | Обязательно |
| AG-12 | **Power** ТВ через ADB (вкл./выкл./reboot — уточнить команды по модели ТВ) | Обязательно |
| AG-13 | Heartbeat + health: CPU/диск/кэш/HLS/ТВ status → Rails | Обязательно |
| AG-14 | Опционально: screenshot / short record (как Stats API) | Желательно |
| AG-15 | Работа при потере WAN: эфир из кэша до исчерпания окна N | Обязательно |
| AG-16 | Не использовать UDP/RTP/RTSP к ТВ | Обязательно |
| AG-17 | Логирование apply/ошибок ADB/HLS; ротация логов | Обязательно |
| AG-18 | Обновление агента (механизм TBD: deb/systemd/container) | Желательно |

### 16.4. Контракт с Rails (черновик)

