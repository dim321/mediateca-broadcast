## 2. Контекст и цели



### 2.1. Бизнес-цели (выведены из ТЗ)

1. Централизованно управлять парком экранов в партнёрских сетях.
2. Размещать коммерческий, собственный и нейтральный контент с учётом квот эфирного времени.
3. Давать организациям изолированный ЛК с ролями, фильтрами и отчётностью.
4. Обеспечивать непрерывную управляемую работу устройств (питание/включение/мониторинг).
5. Масштабировать модель признаков (тегов) без жёсткой иерархии фильтров.
6. (Перспектива) Подключить ИИ для классификации контента (сфера деятельности и др.).



### 2.2. Границы (зафиксировано)

**In scope:**

- Регистрация мониторов/станций, ориентация, признаки
- Целевое железо экрана: **Android TV**
- Загрузка статичных макетов и видео (до Full HD / 4K); prep `.ts` после загрузки
- Шаблоны статичных изображений с редактируемыми зонами
- Ротации / `ScheduleItem` (`loop` / `exact` / `fill`), вставки, автозаполнение; медиаплан = ротация ↔ группа точек ↔ расписание
- Разделение эфирного времени между организациями/типами контента
- ЛК клиента: адаптивная вёрстка + **PWA** (мобильный канал = PWA ЛК, не native-приложение)
- Роли, мультиорганизационность, несколько баз вещания
- Отчёты: выходы, загруженность, финансовые калькуляторы; экспорт XLS/PDF
- **Хаб** + **Агент** (Rails); раздача медиа со станции на Android TV локации (**протокол — TBD**); минимум кабелей (кроме 220В)
- Управление питанием/включением монитора через ADB TV

**Out of scope (отдельные проекты / вне данного ТЗ):**

- CMS для динамических меню вне шаблонов — **отдельный проект**; детали реализации здесь не рассматриваются
- Native мобильное приложение (заменено PWA ЛК)
- Биллинг/онлайн-оплата сразу после брони (оплата после фиксации **не требуется**; фин.отчёты — в scope)
- Юридические/лицензионные аспекты контента

## 3. Стейкхолдеры и роли



### 3.1. Модель владения и тенантов (зафиксировано)

- **Заказчик системы** = оператор рекламной сети.
- **Все точки принадлежат только оператору**; он владелец парка экранов.
- **Клиент сети** = отдельная организация со своим ЛК (тенант).
- Точка **не** принадлежит клиенту; на одной точке могут быть эфирные блоки нескольких клиентов.
- **Клиент видит весь парк точек** оператора (каталог для выбора).
- Клиент **самостоятельно выбирает и бронирует свободные квоты/эфирные блоки** на точке.
- В содержимом эфира клиент видит **только свой** забронированный блок (не чужой эфир).



### 3.2. Роли в ЛК клиента (зафиксировано)


| Роль (код)      | Права в ЛК клиента                                                                                                     |
| --------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `manager`       | Загрузка роликов; формирование **ротаций**; именованные **группы точек**; бронирование квот; **медиапланы**; **отмена и перенос** квот |
| `accountant`    | Доступ к финансовым отчётам                                                                                            |
| `administrator` | Весь функционал ЛК клиента                                                                                             |


Возможность **добавлять роли** и **настраивать права** без перестройки ядра сохраняется.

### 3.3. Оператор сети (зафиксировано)

- Сотрудники оператора работают **только в Avo**.
- Отдельный ЛК оператора **не нужен**.
- **«Режим клиента»**:
  - **one-click из Avo** с **сохранением сессии Avo**;
  - в ЛК оператор действует с правами роли `administrator` **клиента**;
  - в аудите фиксируется **«сделано оператором X»** (не маскируется под пользователя клиента).
- В Avo оператор видит **все устройства**, **всех клиентов**, **все квоты всех клиентов**; может **отменять и переносить** брони клиентов.



### 3.4. Бронирование квот (зафиксировано)

- Бронирование слота — **мгновенная фиксация** (без hold/таймаута/модерации до закрепления).
- Объект брони — квота на **группе точек трансляции** (под проигрывание ротации в рамках медиаплана).
- Конфликт на один слот при **первичной** брони: **first-write-wins**.
- Зафиксированную бронь можно **отменить** или **перенести** (`manager` клиента; оператор в Avo).
- **Перенос**:
  - возможен на **любую точку / группу** парка;
  - **только на предварительно свободный** целевой слот (занятый — перенос невозможен, исходная бронь сохраняется);
  - приоритет «уже держал старый слот» на целевой **не переносится** (F12);
  - на захват свободного целевого слота действует **first-write-wins** (F14) — как при новой брони.



### 3.5. Аутентификация в ЛК (зафиксировано)

- Пользователь входит в ЛК организации по **логину и паролю**.
- Учётная запись привязана к **организации** и **роли**.
- Права в ЛК определяются ролью (§3.2).
- Оператор в «режиме клиента»: one-click из Avo, права `administrator` клиента, аудит «оператор X» (§3.3).
- **Оплата непосредственно после фиксации брони не требуется** (бронь ≠ платёж).

> Ранее (п.10.1.3) допускалось «на старте все права у всех ролей» — **снято** решением F3: роли в ЛК разграничены сразу.

## 7. Пользовательские сценарии (сквозные)



### US-A. Запуск точки

Админ регистрирует локацию → экран(ы) → ориентацию → признаки → делит эфирное время между орг-циями → назначает нейтральный пул.

### US-B. Коммерческое размещение (медиаплан)

`manager` клиента в ЛК:

1. загружает ролики в медиатеку;
2. компонует **ротацию** (именованный набор роликов);
3. создаёт именованную **группу точек трансляции**;
4. бронирует квоту на группе в нужное время (**мгновенная фиксация**; при гонке — first-write-wins);
5. получает **медиаплан** — привязку ротации к группе точек по расписанию.

Оператор работает в Avo; при необходимости заходит в ЛК клиента («режим клиента»).

### US-C. Циклический день

Система на точке собирает 20′ блок (`mode=loop`): коммерция в подблоках + нейтральные прослойки (`fill`; при малом пуле повтор допустим) → крутит цикл; в HH:MM вставляет `exact`-ролики (приоритет timed).

### US-D. Меню в кафе

Оператор выбирает шаблон → правит зоны (блюдо, цена, фото) → публикует на экраны с признаком `меню`.

### US-E. Отчётность

Менеджер выгружает справку выходов / упрощённую справку / фин.разбивку / загруженность.

### 9.2. Упрощения без потери ценности

1. **Признаки = теги + фасеты**, не отдельная «БД признаков». Параллельная фильтрация = комбинация AND между выбранными фасетами / OR внутри фасета (зафиксировать семантику один раз).
2. **Иерархия обязательна**: `Location → Station → Screen` (станция не опциональна).
3. **Ротация v1** = упорядоченный список ассетов (в коде MVP — `Playlist`); «циклический блок 20′» = *генератор расписания* (job/сервис), а не ручной конструктор каждый день.
4. **Нейтральный контент** = ротация/пул с политикой `random_no_repeat_day` (при малом пуле — повтор допустим), подключаемый как filler-policy к квоте.
5. **Timed vs cyclic** → **принято**: единая модель `ScheduleItem { priority, window, mode: loop|exact|fill }` (при конфликте приоритет у `exact` / timed-вставки).
6. **Шаблоны** отложить: на первом этапе — готовые статичные PNG/JPEG из дизайна; зоны — когда появится поток «меню каждый день».
7. **Финансы** вынести из core-эфира: отчётный модуль на play log + формула; не блокировать эфир.
8. **Power management** — через **ADB TV** в Агенте (после стабильного edge runtime).
9. **Sync / транспорт до ТВ** — **не фиксируем** в ТЗ на этом этапе: тест HLS показал сильный рассинхрон; выбор технологии и параметры drift — после повторного тестирования.
10. **ИИ** — асинхронная классификация тегов; не в UX критического пути загрузки.



### 9.3. Архитектура edge (зафиксировано частично; транспорт — TBD)

```text
Broadcast Hub (Rails: ЛК/PWA + Avo + MediaTranscodeJob + Package API)
        │  пакет эфира (HTTPS / pull API)
        ▼
Станция (Linux) ── Station Agent (Rails, деплой Kamal)
        │  • кэш медиа (скользящее окно N ч)
        │  • раздача на Android TV  ⟵ протокол / sync — TBD (после тестов)
        │  • ADB TV → VLC на Android TV
        │  • power via ADB; health/stats
        ▼
Android TV + VLC
```


| Решение                      | Статус                                                                 |
| ---------------------------- | ---------------------------------------------------------------------- |
| Sync (drift)                 | **Отложено** — тест HLS: сильный рассинхрон; параметры после тестов    |
| Плеер VLC + ADB TV           | **Принято** (основной)                                                 |
| Кэш на станции               | **Принято**                                                            |
| Трансляция / протокол до ТВ  | **Снято с ТЗ** (ранее HLS «принято»; 2026-08-01 отменено) — вернём после тестов |
| Станционный агент            | **Принято**: Rails-приложение, Kamal, API к Хабу; §16                  |
| Multicast UDP                | Исторически **не работал** на проверенных ТВ (§15); не выбирать без валидации |

## 15. Наследие legacy-стека

> Источники: `tmp/stack.md`, `tmp/README_STREAM_GUIDE_RU.md` (июль 2026).  
> Работающая система на shell + ffmpeg + VLC/ADB; перестраиваем на **Хаб (Rails)** + **Агент (Rails)** + **Android TV**. Веб-ЛК в legacy «не наш».  
> **Важно (2026-08-01):** раздел — **исторический опыт** и prep-пайплайн. **Выбор протокола трансляции** со станции на точки в этом ТЗ **не фиксируется** (тест HLS — сильный рассинхрон устройств); решение вернём после повторного тестирования.



### 15.1. Целевая и фактическая архитектура legacy

**Целевой пайплайн (из гайда; исторический кандидат, не решение ТЗ):**

```text
Веб-морда → POST manifest + video
  → GPU/prep-сервер: ffmpeg encode ОДИН РАЗ → .ts (GOP=25) + package.json
  → rsync → стрим-сервер: concat -c copy → HLS -c copy → httpd :8080
  → ADB → VLC на Android TV (HTTP HLS)
```

**Факт сейчас (временное):** один стрим-сервер часто **перекодирует на лету** (GOP исходников=50) → CPU ~60–80%; целевое prep с GOP=25 и раздача `-c copy` → CPU ~1–2%.

**Синхронизация ТВ при HLS (наблюдения):** в legacy-гайде ожидался drift ~**0.5–2 с**; **повторное тестирование (2026-08)** показало **сильную рассинхронизацию** между устройствами → HLS **не принимаем** как транспорт в ТЗ до новых тестов.

### 15.2. Критический constraint: MediaCodec на Android TV

На проверенных ТВ (MediaTek/Realtek + VLC 3.0.21) — **исторические** результаты:


| Транспорт                   | Результат (legacy)             |
| --------------------------- | ------------------------------ |
| HTTP static `.ts` / chunked | ✅ Работает                     |
| **HLS (HTTP)**              | ✅ Воспроизведение работает; ❌ **сильный рассинхрон** устройств в тестах 2026-08 |
| UDP / RTP multicast         | ❌ MediaCodec падает            |
| RTSP                        | ❌ падает                       |


Симптомы UDP/RTSP: `AMediaCodec.dequeueOutputBuffer failed`, артефакты, чёрный экран.  
**Вывод для Хаба/Агента:** не строить edge на multicast/UDP/RTSP без отдельной валидации на целевом железе. **Базовый протокол раздачи на ТВ в ТЗ не выбираем** до завершения тестирования.

### 15.3. Профиль кодирования (prep в Хабе)

> Профиль prep `.ts` остаётся полезным для единообразия флота независимо от финального транспорта; привязка «только ради HLS `-c copy`» — **не требование ТЗ** до выбора протокола.


| Параметр         | Значение                                | Зачем                                   |
| ---------------- | --------------------------------------- | --------------------------------------- |
| Видео            | H.264 High, 1920×1080, 25 fps           | Единый формат флота                     |
| **GOP / keyint** | **25** (1 с), `sc_threshold=0`          | Сегментация / keyframe-aligned playback |
| Битрейт          | ~5 Mbps CBR                             | Стабильный стрим                        |
| Аудио            | AAC 128k, 48 kHz, stereo                |                                         |
| Контейнер        | MPEG-TS, `+resend_headers`              | SPS/PPS на IDR                          |
| PTS              | `-muxdelay 0 -muxpreload 0`, `+genpts`  | Иначе VLC: «picture way too early»      |
| Склейка роликов  | `ffmpeg concat -c copy` (не `cat *.ts`) | Нормализация PTS                        |


**Правило:** encode в **Хабе** (job сразу после загрузки в ЛК) **один раз** → `.ts`; на станции — без re-encode где возможно (`-c copy` / concat). Статус файла обновляется по окончании обработки.

Опционально: VAAPI (`h264_vaapi`) на GPU-хосте; в текущем железе i915/VAAPI часто не настроен → fallback CPU libx264.

### 15.4. Что переиспользуем в Хабе / Агенте


| Legacy                                  | Как использовать у нас                                           | Куда ложится                                        |
| --------------------------------------- | ---------------------------------------------------------------- | --------------------------------------------------- |
| **Двухэтапный пайплайн** prep → stream  | Job транскода + артефакты; edge только копирует/раздаёт          | Active Job + object storage                         |
| **Профиль GOP=25 / PTS=0**              | Единый media profile                                             | `MediaTranscodeJob` / ADR encoding                  |

## 16. Требования к станционному агенту (Station Agent)

> Агент — **отдельный репозиторий**: приложение на **Ruby on Rails**, деплой на станцию через **Kamal**.  
> Взаимодействие с **Broadcast Hub** — по **API**.  
> Хаб — источник правды по эфиру, квотам, медиатеке; Агент — edge runtime и раздача на Android TV локации.  
> **Транспорт до ТВ и параметры sync — TBD** (2026-08-01: HLS снят с ТЗ после тестов на рассинхрон); требования ниже без привязки к конкретному протоколу.



### 16.1. Назначение

Rails-приложение на **Linux-станции** в локации:

1. Получает по API и **кэширует** пакет эфира (скользящее окно N часов).
2. **Раздаёт** медиа на локальные Android TV (**протокол — TBD** после тестирования).
3. Управляет **VLC** на ТВ через **ADB TV** (старт URL/потока, контроль сессии).
4. Выполняет **power management** экранов через **ADB TV**.
5. Отдаёт **health/stats** в Хаб / Avo.
6. Деплоится и обновляется через **Kamal**.



### 16.2. Границы ответственности


| В scope Агента                              | Вне scope (Хаб / другое)                         |
| ------------------------------------------- | ------------------------------------------------ |
| Кэш медиа на диске станции                  | ЛК клиента, роли, квоты, бронирование            |
| Применение package / каналы                 | Транскод GOP=25 (prep job в Хабе после загрузки) |
| Раздача медиа на Android TV (**протокол TBD**) | Биллинг, отчёты, финансы                      |
| ADB TV → VLC, power                         | Создание медиапланов                             |
| Локальный мониторинг ТВ                     | Мультитенантная изоляция данных                  |
| Регистрация станции / heartbeat             | UI Avo (Агент — только API)                      |
| Деплой/обновление через Kamal               | CMS динамических меню (вне ТЗ)                   |
