# Хранение медиаплана-заказа, портрета эфира и плейлиста в БД

Документ фиксирует решения по хранению трёх связанных сущностей из ТЗ «Медиаплан и плейлист»: медиаплан как документ-заказ (образец — PDF «Триумф»), портрет плейлиста (эфирная сетка) и ежедневный материализованный плейлист точки вещания. Свёрнуто с работающим продуктом: существующий `MediaPlan` — календарный слот занятости эфира, плейлист сейчас виртуальный (`Agent::PackageBuilder` собирает манифест на лету), портрета эфира нет.

Источники: `tmp/Медиаплан и плейлист.md`, `tmp/2060.Медиаплан для ролика - Триумф.pdf`, `docs/brainstorms/2026-08-22-cabinet-requirements-brainstorm.md`, `CONCEPTS.md`, `docs/solutions/architecture-patterns/media-plan-as-airtime-slot.md`.

## What We're Building

Три новых контура хранения поверх существующей эфирной механики:

1. **Заказ на размещение** — коммерческая правда: контрагент, продукт, ролик, сетка «место размещения × дни → выходы», цены, суммы, статус модерации. Основа печатной формы (приложение к договору, ЭДО).
2. **Портрет эфира** — шаблон структуры эфира станции: циклический тип с частотой блока в час, блоки рекламы/нейтралки/вставок/сервисных шапок, стратегия перебора нейтрального контента.
3. **Плейлист** — ежедневный материализованный документ на станцию: версия, позиции с таймингом и происхождением (медиаплан / добивка / вставка / сервис).

## Why This Approach

Рассмотрены варианты по каждой развилке:

- **Связь заказа со слотом:** эволюция `MediaPlan` (размывает инварианты слота коммерческими данными); параллельный документ (два источника правды об эфире). Выбрано: **заказ порождает слоты** — эфирная механика (FWW, `ScreenLock`, `ScreenOverlapGuard`, квоты) не трогается, заказ разворачивается в существующие слоты через `Airtime::OccupyWithPlan`.
- **Плейлист:** on-the-fly + снапшот выдачи (нет «плейлиста на завтра», недетерминированная ротация нейтралки); кэш с инвалидацией (сложная логика). Выбрана **материализация** — прямо соответствует ТЗ («внутренний документ, ежедневно, на несколько дней вперёд, принудительное обновление»), даёт аудит и воспроизводимость.
- **Портрет эфира:** jsonb-документ по прецеденту `locations.operating_hours` (слабая ссылочная целостность: блоки ссылаются на ротации). Выбраны **нормализованные таблицы** — FK на ротации, запросы «где используется ротация», частичное обновление блоков.
- **Сетка дат заказа:** jsonb-сетка на строке (план/факт по дням через `jsonb_each` — громоздко). Выбраны **нормализованные дневные записи** — индексы, SQL-агрегации для отчётов и эфирных справок, естественная разреженность (прочерк = нет строки).
- **Нейминг:** переименование слота в `AirtimeSlot` (рефакторинг по всему коду и UI). Выбрано: документ получает **новое имя** (`AdvertisingOrder`), слот остаётся `MediaPlan`.

## Key Decisions

### Заказ на размещение

- `advertising_orders` — шапка: `organization_id` (контрагент = организация-клиент; для «своего контента» — организация менеджера по умолчанию), `created_by_user_id` (автор фиксируется автоматически), `product_name`, `business_sphere_id` (пополняемый справочник-номенклатура), `media_asset_id` (ролик), **снапшот** `clip_title` + `duration_seconds` (печатная форма исторически стабильна даже при замене ролика в медиатеке), `coefficient_percent`, `discount_cents`, денормализованные итоги `total_shows` / `total_sum_cents`, строковый enum `status` (draft / pending_moderation / active / completed / cancelled).
- `advertising_order_lines` — строка = место размещения: `broadcast_point_group_id`, `price_per_day_cents`, итоги строки; unique `(order_id, group_id)`.
- `advertising_order_line_days` — `(line_id, date) → shows`, unique по паре, check `shows > 0`. Прочерк в сетке = отсутствие строки.
- Деньги — integer в копейках (`*_cents`). Итоги хранятся денормализованно и пересчитываются сервисом при изменении строк — печатная форма и списки не должны считать суммы на лету.
- Разворачивание в эфир: сервис `Orders::UnfoldIntoSlots` схлопывает непрерывные цепочки дней строки в окна, вычисляет `shows_per_hour = shows / часы работы локации` и занимает слоты через `Airtime::OccupyWithPlan` (все его инварианты сохраняются). `media_plans` получает nullable `advertising_order_line_id` — слоты, созданные вручную, имеют NULL; обратная совместимость полная. Отмена заказа = soft-cancel порождённых слотов (существующий механизм).
- Печатная форма (приложение к договору) — потребитель хранимых полей, не драйвер схемы; все её данные (шапка + сетка + итоги + скидка + подписи) покрыты шапкой, строками и днями.

### Портрет эфира

- `broadcast_portraits` — `station_id` (nullable: NULL = шаблон, копируется при заведении точки — «портрет строится один раз»), `name`, строковый enum `kind` (`cyclic`; `timed` — резерв следующей итерации), `block_frequency_per_hour` (1..60; типовые 1/2/3/4/5/6/10/12/20), `max_commercial_in_row` (по умолчанию 3), `neutral_min_seconds` (5 или 10 — открытый вопрос заказчика, хранится здесь).
- Привязка к **станции**, а не к экрану/группе: станция — единица вещания и доставки пакетов (агент аутентифицируется токеном станции), экраны за одной станцией могут входить в разные группы.
- `broadcast_portrait_blocks` — `position` (порядок в цикле, unique в портрете), строковый enum `kind`:
  - `commercial` — приоритетная база: все активные слоты станции (без `rotation_id`);
  - `filler` — вспомогательная база: `rotation_id` (FK) + `pick_strategy` (sequential / random / ordered);
  - `insertion` — «вставка» на точное время: `time_of_day` + `rotation_id`;
  - `service_header_start` / `service_header_end` — сервисные шапки рекламного блока по закону.
- Ротация нейтрального контента **детерминирована от даты**: sequential — смещение по номеру дня; random — seeded PRNG (seed = станция + дата). Воспроизводимо без хранимого состояния; «по порядку» из ТЗ = `ordered`.

### Плейлист

- `playlists` — `station_id`, `for_date`, `version`, строковый enum `status` (current / superseded), `generated_at`, `etag` (для agent API, преемник etag `PackageBuilder`). Partial unique index `(station_id, for_date) WHERE status = 'current'` — одна текущая версия на станцию/день (прецедент: partial unique на `organizations`).
- `playlist_items` — `position`, `media_asset_id` (FK `on_delete: :restrict`, прецедент `rotation_items`: нельзя удалить ролик из выданного плейлиста), тайминг в секундах от начала эфирного дня станции, `source_kind` (media_plan / filler / insertion / service) + nullable `media_plan_id` — происхождение позиции для отчётов.
- Генерация: `Playlists::GenerateForDate` (domain service) из recurring-задачи Solid Queue (`config/recurring.yml`, ночью по TZ станции, горизонт = `offline_cache_hours`) + принудительная регенерация точки/группы. Точка расширения: `Airtime::OccupyWithPlan` / `Reschedule` / `Cancel` триггерят регенерацию затронутых станций и дат.
- `Agent::PackageBuilder` переключается на чтение текущей версии плейлиста; fallback на сборку на лету, если плейлиста нет (мягкая миграция флота).
- **Хранение плейлистов агрессивно ограничено (~14 дней, recurring-очистка).** Эфирные справки строятся как план (дни заказа) против факта (`PlayLog`), а не по плейлистам. Иначе при целевых 10 000 точек позиции дадут ~3 млн строк в день.

### Сквозные решения

- Все новые операции — `ServiceObject` в `app/domain/orders/`, `app/domain/portraits/`, `app/domain/playlists/`; тонкие контроллеры; Pundit-политика на каждую новую модель.
- Строковые enum'ы, check-constraints, явные FK с `on_delete:` — по паттернам существующих миграций.
- Тип `timed` («эфир по времени», жёсткий хронометраж 10/20/30 сек) в первую итерацию **не входит** — прямо отложено в ТЗ; схема портрета его допускает через `kind`.

## Open Questions

1. Делимость выходов: 36 выходов/день ÷ часы работы локации — что при неделимости (ошибка, округление, неравномерное распределение по часам)? Влияет на `Orders::UnfoldIntoSlots`.
2. Нейтральный минимум — 5 или 10 секунд (уже открыт в брейншторме 22.08)? Хранится в `broadcast_portraits.neutral_min_seconds`.
3. Печатная форма: HTML-печать из браузера на первой итерации или PDF-генерация (для ЭДО)? В проекте PDF-стека нет.
4. Замена ролика в живом заказе (открытый вопрос 22.08): перегенерация затронутых слотов и плейлистов или запрет?
5. Скидка и коэффициент: оба на шапке заказа; нужен ли коэффициент на строке (в PDF он общий)?
6. Модерация чужого эфира: статус `pending_moderation` заложен, но сам флоу модерации — предмет отдельного брейншторма (дельта 22.08).
